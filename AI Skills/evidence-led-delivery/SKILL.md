# Evidence-led delivery

Work toward a result someone can open, run, inspect or act on. This workflow transfers observable practices between assistants. The host supplies the available tools, permissions, effort settings and collaborators. On a small request, one source check and one direct test may be the whole job.

## Define completion from the recipient’s side

Identify who will use the result, where they will find it and what they will do first. Turn the user’s concrete constraints into checks. For “a five-person talk that works without Wi-Fi,” look for five named handoffs, a script timed to the short route and a presentation that opens after extracting the delivered archive with networking disabled. For a question about a claim, the deliverable may be a two-sentence answer and its source.

When the user says “continue” or adds a correction, inspect the current artifacts and the last verified state. Carry the existing commitments forward. Preserve completed work and changes others have made. A correction about exhibit copy authorizes work on that copy and its dependent exports. Altering the underlying product is a separate decision.

## Choose evidence that can settle the question

Start with the project’s own instructions and the nearest relevant source or artifact. Follow a specific path from an input to an output. Search broadly for missing callers or records only when the answer depends on their absence.

| What the user needs to know | What to inspect or run |
| --- | --- |
| What was intended or attributed | Dated design record, approved brief, manuscript, license or credited author list |
| What currently happens | Call site, inputs, implementation, persistence and actual user entry point |
| What a generated artifact contains | Open the final file or extracted package and inspect the rendered content |
| What a measurement establishes | Inputs, population, units, environment, method and output of the run |

If two sources disagree, ask which question each can answer. A design note can document intent. A handler and its callers can establish which operation is wired today. A controlled run establishes an observed result for its conditions. Express the remaining uncertainty in ordinary words. Give a short decision and its evidence when the distinction changes the deliverable.

## Divide work where ownership is clear

Resolve shared names, data formats and interfaces early. Parallelize independent investigations or edits when the host supports collaborators and the work saved exceeds coordination cost. Give each contributor the result, owned paths, shared interface, acceptance check and boundaries. One person owns integration and shared files. A reviewer can independently check the same path read-only.

For example, one contributor owns road footage, another owns the station map and a third owns the radio animation. Agree on the scene IDs, visible control labels, operating states and output paths. The integrator owns the rehearsal script and release archive. A result message should supply changed paths, the exact test and outcome, and anything still pending. Review the files themselves before relying on the message.

With one assistant, use the same boundaries as successive passes. Resolve the most consequential unknown first, implement the dependent work, then review from the recipient’s entry point. A separate validation method such as parsing an export, opening a clean browser or manually tracing a counterexample can expose a mistake that repeating the same build misses.

## Make a decision and carry it through

Compare candidates when the choice changes fidelity, risk, effort or usability. For an animation that stutters on a venue computer, measure elapsed playback time and frame delays on that path. A fixed cinematic shot can be pre-rendered with scrubbing and captions. A board that the user needs to rotate calls for interactive geometry. Test the chosen solution against the original failure.

Use the existing stack, sources and reversible edits where they fit. After a failure, record which step failed, inspect its output, change the relevant condition and retry. Resume from artifacts and process state after an interruption. Before repeating an external side effect, check its receipt or current state. Continue independent work while a genuinely blocked part awaits input. Ask the user when a missing permission, source or irreversible choice changes what can be delivered.

## Verify the item being handed over

Exercise the recipient’s exact entry point using representative content. Include a counterexample capable of revealing the particular error being claimed fixed. For a data report, recompute totals from rows and inspect labels and denominators. For a UI, use its actual controls and inspect a visual frame at the target size. For a release, test the exported or extracted copy after the last relevant change. Apply the project’s existing gates and record any material untested boundary.

Reconcile the pieces before delivery. Compare UI labels to the script, model revision to its caption, units to their source, links to the actual files, and packaging to the assets exercised. Rebuild the dependent outputs when a late correction changes an input.

Hand over the actual artifact or answer, the test result that matters to its recipient, and consequential assumptions or remaining limits.
